# 增产策略优化算法详解

> 本文档详细描述在 DAG 层级动态变化约束下，寻找全局最优增产策略的优化算法。
> 配合 `code-analysis.md` 第12节阅读。

---

## 1. 问题背景

### 1.1 DAG 层级的两层功能

| 功能 | 说明 |
|------|------|
| **遍历顺序** | 按 DAG 顺序（低→高）遍历增产选择，可实现完美剪枝 |
| **计算顺序** | 给单次资源消耗计算提供迭代顺序（上游先算） |

### 1.2 核心矛盾

增产剂本身是物品，有自己的生产链。**选择增产剂 = 添加新的原料依赖**。

规则：`产物DAG层级 > 所有原料的DAG层级`

因此：低 DAG 物品选择了高 DAG 增产剂 → 增产剂层级被拉低 → DAG 结构变化。

这形成了**循环依赖**：遍历顺序依赖 DAG，DAG 依赖增产选择。

---

## 2. 关键洞察

> **不需要等所有低层级物品都确定，只需要等该物品的所有上游物品确定即可。**

- 优化遵循 DAG 层级顺序的**本质逻辑**：先确定原料的增产策略，再确定产物的
- 这样数学上可以证明与全局最优增产策略相符
- 但"所有低层级物品都确定"是充分条件，不是必要条件
- **上游物品必然在更低层，但更低层的物品不全是上游**——这是包含关系

---

## 3. 优化算法

### 3.1 算法概述

在最高等级配置下按 SCC 顺序完成所有物品的优化：

1. **初始化** - 强制所有物品使用最高等级增产剂
2. **SCC 分析** - 在最高等级配置下分析 SCC 结构
3. **按 SCC 顺序优化** - 单节点逐个优化，循环组坐标下降

这种设计使得算法逻辑更简洁，无需多阶段迭代。

### 3.2 算法流程

```
optimizeProliferatorStrategy(gameData, schemeData, settings, needs, strategy='min_power'):

  1. 初始化
     - 根据 strategy 选择目标函数（calculatePower / calculateRawOre / calculateFootprint）
     - 构建物品→配方映射
     - 计算初始目标值

  2. SCC 分析
     - 在最高等级配置下计算一次 SCC
     - 按 SCC 正序排列（底层在前，顶层在后）

  3. 按 SCC 顺序优化
     - 遍历每个 SCC：
       - 单节点 SCC：逐个优化，尝试所有增产选择，选择最优
       - 多节点 SCC（循环组）：坐标下降优化
     - 每个物品优化后立即持久化到 resolved Map

  4. 返回最优方案
```

### 3.3 核心函数

```javascript
// 按 SCC 顺序优化
async function optimizePhaseBySCC(sccs, gameData, settings, needs, currentScheme, itemToRecipe, resolved, onLog, strategy) {
  for (const scc of sccs) {
    if (scc.size === 1) {
      // 单节点 SCC：逐个优化
      const itemId = [...scc][0];
      // 尝试所有增产选择，选最优
      // 持久化到 resolved
    } else {
      // 多节点 SCC（循环组）：坐标下降优化
      const cycleItems = [...scc];
      const cycleResult = await optimizeCycleGroupPhase(cycleItems, ...);
      // 持久化循环组策略
    }
  }
}
```

## 4. 单节点优化

对于单节点 SCC（非循环组物品），逐个优化：

```
对于每个单节点物品：
  bestChoice = 无
  bestCost = Infinity
  对于物品的每种增产选择 choice：
    临时应用 choice
    计算新成本
    如果新成本 < bestCost：
      更新 bestChoice 和 bestCost
  应用 bestChoice
  持久化到 resolved Map
```

### 单选择物品处理

当物品只有一个增产选择时（如被限制加速后只能选"无"），直接应用该选择，无需遍历。

## 5. 循环组坐标下降算法

### 5.1 算法原理

每次固定其他物品的选择，只优化一个物品，反复迭代直到收敛。

### 5.2 算法伪代码

```
function optimizeCycleGroup(group, gameData, settings, needs, baseSchemeData, strategy):
  // 1. 初始化：所有物品选择"无"
  currentChoices = group.map(item => { level: 0, mode: 0, name: '无' })
  currentCost = calculateObjective(currentChoices, strategy)
  
  // 2. 迭代优化
  improved = true
  round = 0
  while improved:
    improved = false
    round++
    improvedCount = 0
    
    for each item in group:
      bestChoice = currentChoices[item]
      bestCost = currentCost
      
      for each choice in getAvailableChoices(item):
        if choice == currentChoices[item]: continue
        tempChoices = currentChoices.copy()
        tempChoices[item] = choice
        cost = calculateObjective(tempChoices, strategy)
        if cost < bestCost:
          bestCost = cost
          bestChoice = choice
      
      if bestChoice != currentChoices[item]:
        currentChoices[item] = bestChoice
        currentCost = bestCost
        improved = true
        improvedCount++
  
  // 3. 持久化结果
  persist(currentChoices, currentCost)
```

### 5.3 复杂度

- O(items × choices × passes)
- 典型情况：10物品 × 4选择 × 3轮 = 120次计算
- 相比暴力枚举：120 vs 1,048,576（减少 99.99%）

### 5.4 收敛性

- 每次改善严格降低目标值
- 选择数有限，必然在有限步内收敛
- 典型 2-3 轮收敛

## 6. 多目标策略支持

### 6.1 支持的策略

| 策略标识 | 名称 | 目标函数 | 说明 |
|---------|------|---------|------|
| `min_power` | 最小电力 | `totalEnergyCost` | 最小化总耗电（默认） |
| `min_raw_ore` | 最小原矿 | `totalRawOre` | 最小化原矿消耗总量 |
| `min_footprint` | 最小占地 | `totalFootprint` | 最小化总占地面积 |

### 6.2 原矿识别逻辑

原矿判定标准（与 `result.jsx` 一致）：

1. 物品在 `settings.mineralize_list` 中（用户标记为原矿化）
2. 物品的配方无原料输入且只有单一产物（天然原矿，如铁矿、铜矿等）

### 6.3 策略对算法的影响

不同策略仅影响目标函数的选择，优化算法结构保持不变：

```javascript
// 根据策略选择计算函数
const calculateResult = strategy === 'min_raw_ore' ? calculateRawOre :
                        strategy === 'min_footprint' ? calculateFootprint :
                        calculatePower;

// 获取目标值
function getObjectiveValue(result, strategy) {
  if (strategy === 'min_raw_ore') return result.totalRawOre ?? 0;
  if (strategy === 'min_footprint') return result.totalFootprint ?? 0;
  return result.totalEnergyCost;
}
```

## 7. 持久化与剪枝

### 7.1 持久化的正确性

当一个物品（或循环组）的**所有上游都已确定策略**后，遍历其所有增产选择得到的最优策略可以**永久持久化**。

原因：上游不会再变 → 局部最优 = 全局最优 → 不可推翻。

### 7.2 持久化策略

- **单节点优化**：每个物品确定最优策略后立即持久化到 `resolved` Map
- **循环组优化**：循环组内所有物品的最优策略在坐标下降收敛后统一持久化

### 7.3 剪枝效果

```
物品持久化后 -> 不再参与后续优化
-> 减少重复计算，提高效率
```

## 8. 算法特性

### 8.1 算法优势

| 特性 | 说明 |
|------|------|
| **逻辑清晰度** | 按 SCC 顺序优化，逻辑简洁 |
| **效率** | 只进行一次 SCC 分析 |
| **精确性** | 循环组用坐标下降遍历，覆盖所有可能 |
| **可维护性** | 无多阶段状态管理，代码简洁 |
| **可扩展性** | 支持多种优化目标函数 |

### 8.2 完整性

- **不遗漏**：所有物品的所有增产选择都会被尝试
- **必然终止**：坐标下降算法在无改善时停止，保证收敛
- **最优性**：按 SCC 顺序保证上游先确定，局部最优 = 全局最优

### 8.3 复杂度

#### 单节点优化

- 时间复杂度：`O(K * M)`
  - K：单节点物品数
  - M：每个物品的增产选择数（最多 7）
- 空间复杂度：`O(1)` 逐个处理

#### 循环组优化

- 时间复杂度：`O(C * N * M)`
  - C：坐标下降迭代次数（通常 < 10）
  - N：循环组物品数
  - M：每个物品的增产选择数（最多 7）
- 空间复杂度：`O(N)` 存储当前选择状态

#### 总体复杂度

- 远小于 `7^N`（暴力枚举的理论复杂度）
- 实际运行时间主要取决于 SCC 分析和目标函数计算的开销

## 9. 返回值结构

```javascript
{
  optimalScheme: Object,      // 最优方案
  initialPower: number,       // 初始耗电
  optimalPower: number,       // 最终耗电
  strategy: string,           // 使用的策略 ('min_power' | 'min_raw_ore' | 'min_footprint')
  initialObjective: number,   // 初始目标值
  optimalObjective: number,   // 最终目标值
  changes: Array,             // 策略变更列表
  processedCount: number,     // 已处理物品数
  totalCount: number          // 总物品数
}
```
