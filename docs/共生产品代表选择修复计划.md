# 循环依赖共生产品代表选择修复计划

日期: 2026-08-22
状态: 待确认

## 一、目的

修复核心计算引擎在**循环依赖中共生产品对**(同一配方的多个产物同时进入循环组,如 原油精炼 同时产出 氢 和 精炼油)的**副产物归因错误**。

当前算法判定:精炼油为多余产物(-149.66)、氢仍缺 94.2。实际正确结果(用户已验证):**氢为多余产物(-5.63)、精炼油恰好满足(+200.94)**。

## 二、背景与根因

### 2.1 现有算法

循环组(多节点 SCC)用矩阵求逆求解析解。同一配方的多个产物(如 氢+精炼油)成本方程线性相关导致矩阵奇异,因此**合并**为一个"代表物品"进入求逆,另一物品折算为副产物。

### 2.2 根因

合并代表的选取规则为 `representative = items[0]`(**SCC 插入顺序,任意**)。代表选择决定**谁的需求作为矩阵硬约束、驱动配方运行次数**:

- 代表=氢:燃料链的**内生氢需求**(电力→氘核燃料棒→重氢→氢,随生产放大)驱动原油精炼放大到 ~170 次 → 精炼油折算为副产物信用 → 精炼油误判多余,氢仍需外部补 94.2(错误)。
- 代表=精炼油:精炼油需求(塑料链,基本固定)驱动 ~100 次 → 氢折算为副产物 → 氢多余 5.63(正确)。

本质:线性求逆找到一个"失控放大"的不动点(R=170),其联产品多余量是**持续浪费**;而正确的不动点是**生产递归"多余量被消耗完才生产、没消耗完就抵消"的稳定驻点**(R=100,联产品多余量最小且可被内生需求自我消耗)。

### 2.3 已确认的决策(与用户讨论确定)

1. **判定方式**:对共生产品对的每个候选代表,做"**一步递归测量**"——把该候选的联产品视为外部来源(加入过滤列表,整线重算),读取重算结果中联产品的多余量。
2. **判据**:取"联产品多余量 **÷ coOutput**(该联产品单次配方运行产出)"**最小**的候选为胜者代表。
3. **测量时机**:引擎级整线重算(联产品需求来自整条产线,不能只算循环组)。
4. **归一化**:用 coOutput 折算成配方运行次数(比率必须考虑——多余量是不同物品单位,不可直接比较)。

## 三、实现方案

### 3.1 文件改动

#### `src/engine/index.js`(CoreEngine)

1. **calculate 签名扩展**:`calculate(needs, recipes, initialFilterList = new Set(), measurementMode = false)`
   - `initialFilterList`:初始过滤列表(把物品视为原矿)。主计算不传;测量计算传联产品。
   - `measurementMode`:测量模式标志,为 true 时**跳过共生产品组检测**(防递归嵌套)。

2. **共生产品组检测**(主计算,初始化后):
   - 遍历 `this.sccs`,对每个多节点 SCC,按图节点的 `recipeId` 分组;组内 ≥2 物品 → 共生产品组。
   - 先支持**单组**;多组时每组独立处理(后续扩展)。

3. **胜者代表测量循环**(每组):
   - 候选 = 组内每个物品。
   - 对每个候选:联产品 = 组内其他物品。
   - 递归调用 `calculate(needs, recipes, new Set([联产品]), true)`,读取结果的 `resourceUsage[联产品]`。
   - 多余量 = `-resourceUsage[联产品]`(正值);折算运行次数 = 多余量 / coOutput(coOutput 从 `this.recipeMap` 配方 产物 读取)。
   - 取**最小折算运行次数**的候选为胜者;平局(都 ≤0 或相等)回退 `items[0]`。

4. **存储并传递**:`this.coproductRepMap = Map<recipeId, representative>`,传给 `expandInSCCOrder`。

#### `src/engine/unit-cost.js`(expandInSCCOrder / solveSCCByMatrix)

1. `expandInSCCOrder` 接受可选参数 `coproductRepMap = null`。
2. **移除**现有多节点 SCC 分支内的候选循环(`collectMergeCandidates`、`measureCoProductSurplus` 及其比较逻辑)——引擎级测量取代它。
3. `buildMergeMap` 的 `chooseRepresentative` 回调:若该组 recipeId 在 `coproductRepMap` 中,返回其胜者代表;否则默认 `items[0]`。
4. 保留 `buildMergeMap` 的独立函数结构(solveSCCByMatrix 通过参数接收 mergeMap)。

### 3.2 数据流

```
CoreEngine.calculate(needs, recipes)
  ├─ 主计算:
  │    initialize → 图/SCC
  │    检测共生产品组 G(配方R: A+B)
  │    测量候选A: calculate(..., filter=[B], measurementMode=true) → B多余量_b → 运行次数_b
  │    测量候选B: calculate(..., filter=[A], measurementMode=true) → A多余量_a → 运行次数_a
  │    胜者 = min(运行次数_b, 运行次数_a) 对应的代表
  │    coproductRepMap = { R: 胜者 }
  │    主迭代 → expandInSCCOrder(..., coproductRepMap)
  │         solveSCCByMatrix(mergeMap 用胜者代表)
  │         代入 solution → 阶段2 → 过滤迭代 → 最终结果
  └─ 测量计算(measurementMode=true):
       filterList 含联产品 → 联产品视为原矿 → 不触发检测 → 正常迭代 → 返回结果
```

### 3.3 性能

每个共生产品组:2 次测量计算 + 1 次主计算 ≈ **3 倍单次引擎成本**。SCC 规模通常几十节点,单次计算 <100ms,可接受。优化空间(按图结构缓存胜者代表)留作后续。

### 3.4 边界与防护

- **递归防护**:测量计算 `measurementMode=true` 跳过组检测。
- **平局**:两候选折算运行次数相等或都为 0 → 回退 `items[0]`(无反馈场景,两向结果一致,任意皆可)。
- **多组**:先支持单组;多组场景在测量循环中分别处理,候选组合爆炸(2^k)问题后续再议。
- **coOutput 缺失**:配方 产物 中取不到时按 1 处理。

## 五、风险与后续

- 测量计算为整线重算,成本 3 倍;后续可按图结构缓存胜者代表。
- 判据"最小联产品多余折算运行次数"基于生产递归的稳定不动点语义;若未来发现无矛盾错误解案例,该判据本身可作为矛盾检测观测点。
- 多共生产品组组合爆炸,后续单独设计。
